SummaRace v3 · version 1.3.6 (versionCode 17) · how the parts of the app fit together and why

1Overview

This document describes the system as a whole: who uses it, its components, how data moves between them, the main runtime sequences, and the design choices behind them. The TRD lists the tools; this document shows how they work together.

In short, SummaRace is a single-device, offline system. One Android app holds the game, the content and the saved data. The only data that leaves the phone is a CSV file the teacher exports.

7Performance design

ProblemDesign choice
Slow start-up on cheap phonesNothing 3D loads at start-up. The 4.5 MB of models preload in the background 1.5 s after the learner's first tap (Race.warm), so they are usually ready before the first race.
Low frame rate in the raceThe first 2.5 s of a race are timed. Below 22 fps the game switches to low mode: no falling leaves, no sun shadows, less side scenery, pixel ratio 1. Pixel ratio is capped at 1.5 in any case.
Memory growing during a raceObstacles and effects free their GPU geometry, materials and textures when removed; shared models stay.
Loading files from inside the APK3D models and sound clips are base64 text inside .js files, so they load with a script tag even where file fetches are blocked.
Voice delayMira's clips are decoded once and cached in memory.

8Failure handling

If this fails……the game does this
The race cannot start (no WebGL)Mira says the race could not start and the level continues to Story order with a race score of 50% and 0 coins.
A 3D model does not loadSimple shapes made in code stand in for the runner, patrol or trains.
A voice clip is missingThe phone's voice reads the line instead.
localStorage is blocked or fullEvery read and write is wrapped, so the game keeps running; progress is not kept.
Saving the CSV is not allowed (Android 7–9, permission refused)A copy is kept in the app's own folder and the button tells the teacher to use Share CSV.
Teacher erases by mistakeThe last erase is kept and can be brought back, merged with anything recorded since.

9Security and privacy

  • No network code, no analytics, no ads, no accounts. The app asks only for vibration and, on Android 7–9, storage (to save the CSV).
  • Learner data is a name, a section, scores and summaries, kept only on the phone in the app's private storage.
  • Teacher records have no password; ERASE needs a typed word, which guards against accidents, not against learners who deliberately look.
  • The repo is public, so the answer key and all content can be read by anyone. The signing key is kept off GitHub.

11Design decisions

DecisionWhyTrade-off
Web game in a WebView, not a native or Unity appOne code base that runs in a browser for fast testing; small APK (~13 MB); v1/v2 in Unity were heavier.Depends on the phone's WebView and WebGL.
No backendClassrooms may have no internet; no accounts or personal data on a server.Records stay per phone; the teacher must collect CSVs from each device.
Rules-based summary checkerWorks offline and gives the same result every time.Can miss meaning a teacher would catch; the text is saved for the teacher.
Recorded voice instead of live TTSA natural voice on any phone, no download.New lines need recording; the build script was lost.
One big index.html, no framework or build stepNothing to install; easy to recover and patch.A large file to read; modules are separated by comments, not files.
Answers in lanes, no pause (1.3.5+)Keeps the race moving, per the client's last request.Slow readers get 4–9 s of reading time before the gate; still worth a phone test with a slow reader.
