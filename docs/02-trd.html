Technical Requirements Document

SummaRace v3 · version 1.3.6 (versionCode 17)

1Overview

This document lists the tools, technologies and structure used to build SummaRace v3, so anyone who picks up the code knows how it fits together and what it must keep doing.

SummaRace v3 is a web game (HTML, CSS and plain JavaScript, with three.js for the 3D race) that runs inside a small Android app. The Android app is a full-screen WebView plus a JavaScript bridge for things a web page can't do on its own: the phone's voice, the clipboard, sharing, saving files and closing the app.

2Technical goals

  • Works with no internet. Every file is inside the APK. Nothing is fetched from the network.
  • Runs on low-cost phones. Android 7.0+ (API 24), about 2 GB RAM. The 3D models only load when the race starts, and GPU memory is freed after each obstacle.
  • Easy to change. No build step for the game. Stories are one data file. Opening the folder with a local web server runs the game in a desktop browser.
  • Safe for learners. No accounts, no tracking, no ads, no outside links during play.

4Architecture

Script load order

three.min.js → GLTFLoader.js → assets.js → stories.js → words.js → voice/voice.js → the main script inside index.html. The main script is wrapped in one function (an IIFE), so its internals are not global. Each data file sets one global: SR_ASSETS, STORIES, SR_WORDS, SR_VOICE, SR_MODELS.

5Race engine

  • Three lanes at x = −2.2, 0 and 2.2. The runner (Max or Mia, chosen on the start card) is chased by an officer and a dog.
  • A gap meter (0–100) is the distance to the patrol. It starts at 60 and shrinks slowly while running, but not while the learner is reading a question. A right answer adds 24. A wrong answer, a train bump or a barrier hit takes 10–14 away, but these never push the gap below 8: only the slow drain can end the race. At 0 the runner is caught and the race restarts.
  • Each of the 5 SWBST parts is asked in turn. The question and the 3 answers show at the top. The game waits a reading time of 0.35 s per word (4–9 s, 25% less when a missed question comes back), then sends an answer gate down the track. The lane the runner is in at the gate is the answer.
  • Each level has its own seeded course (levelPlan(id)): speed, obstacle rows and spacing grow with the level number, so level 30 is harder than level 1 but each level plays the same every time.
  • Controls: swipe left/right to change lane, up to jump, down to roll. Tapping the left or right third of the screen also changes lane. Keyboard arrows (or A and D) and Space work in a desktop browser.
  • Race score for the level = share of the 5 parts answered right on the first try, kept across "Try the race again".

6Summary checker (offline)

The checker is rules-based on purpose: it has to work offline on a cheap phone. It can miss things a teacher would notice, which is why the summary text and its status go into the CSV for the teacher to read.

7Performance and device rules

  • Start-up was measured at about 0.75 s with the CPU slowed 6× in a desktop browser. The 3D models (4.5 MB) are not part of start-up.
  • Obstacles and effects free their GPU geometry and materials when removed; shared models and textures are kept.
  • Portrait only. The layout uses safe-area insets for phones with a notch.
  • Hardware acceleration is on for the WebView.

8Build, run and release

Run in a browser:
  cd app/src/main/assets/www
  python -m http.server 8000      # then open http://localhost:8000

Build the APK:
  open the repo in Android Studio and build, or run: gradle assembleDebug
  the APK lands in app/build/outputs/apk/
  • Raise versionCode and versionName in app/build.gradle for every release. The next free versionCode is 18.
  • Release APKs are signed with the project's current signing key, which is kept off GitHub on the owner's PC. The original 1.2.0 key was lost, so phones with that old test build must uninstall it once.
  • Never commit the keystore, *.jks, *.keystore or local.properties. They are in .gitignore.

9Testing

  • Day-to-day testing is in a desktop browser at localhost:8000, with the phone size set in the browser's device mode.
  • Automated checks use Playwright with headless Chromium. Because the main code is private inside one function, tests reach it by injecting a small helper before the script ends.
  • An APK is built for a phone test only when a change is ready. Android-only features (voice fallback, Download folder on Android 7–9, Back button) must be checked on a real phone.
